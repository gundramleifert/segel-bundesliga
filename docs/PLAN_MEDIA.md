# Pictures — a small media library with automatic layout

Status: **phase 1 built** (Story R-2), plus from phase 2 the read-time sizes and
captions and a public media page (R-1, R-3, 2026-10-20). Departures from this plan: the
master is the **original upload** (kept privately) rather than a 2400 px JPEG, and a
post's text keeps `/api/media/<name>.webp` rather than `/api/media/<id>`. Galleries,
shapes and focus crops (§3) are still open. Originally: **plan, nothing built** (written 2026-10-19 after editorial found pictures in posts
fiddly: an upload is lost to every other post, the site's pictures are a dropdown of
names, and there is no way to make a picture smaller). Stories come first (`CLAUDE.md`,
"How to update the docs"): this file is what Story R-2 is written *from*. Once the story
exists, it is the truth and this file only says why.

**The idea in one line: the writer says *which* pictures, the site decides *how*.** There
is no size handle, no "align left", no width in pixels — not as a missing feature, but as
the design. Editorial wants to write about a regatta, not lay out a page, and most readers
are on a phone, where every manual layout breaks first.

---

## 1. Decisions this plan rests on

1. **A picture is a library entry, the text only points at it.** An upload becomes a
   `MediaItem` with its alt text, its credit and its measurements; a post's text stores
   `<img src="/api/media/42">` and nothing else about it. The public page fills in the
   rest **when it is read** — alt, credit, sizes, placeholder. So a credit corrected in
   the library is corrected in every post that shows the picture, and a post never holds a
   stale copy. The same rule as points: the source is stored once, everything shown is
   derived (`CLAUDE.md`, Domain decisions).
2. **Layout is computed from the picture, never chosen** (§3). A picture's shape and
   resolution, and whether other pictures stand next to it, decide its size and
   arrangement. The writer's only layout act is the order of things in the text.
3. **Pictures that arrive together are a gallery.** Dropping five photos at once makes
   one gallery, not five pictures down the page; dropping a picture right beside another
   one joins them. A gallery arranges itself (§3.2).
4. **The stored HTML stays dumb.** The editor stores the reference and the cleaner keeps
   only that (`app/services/rich_text.py`: `img` with `src` under `/api/media/`, `figure`
   with `data-gallery`). Everything clever — `srcset`, `width`/`height`, the aspect ratio,
   the caption — is **generated by our own code on read** from library rows, after
   cleaning, so nothing a writer pastes can smuggle a `style` or a size in.
5. **Every picture is re-encoded, at a few fixed widths.** As today (`app/services/
   pictures.py`): upright, no EXIF, never stored as uploaded. New: WebP variants at 480,
   960, 1600 and 2400 px (never wider than the original), so a phone loads ~60 KB where
   it loads 600 KB today. Names are random, so every variant is cached `immutable`.
6. **Editorial only**, like posts (Story R-1). Clubs get a library of their own only when
   they get pages of their own; the model leaves room (`MediaItem.owner`), the plan does
   not build it.

## 2. The library

### 2.1 What an entry knows

| Field | Where it comes from |
|---|---|
| picture + variants | the upload, re-encoded (§1.5) |
| `width`, `height` | measured after the upright turn |
| `placeholder` | the picture's average colour, or a tiny blur (BlurHash) — shown until it loads, so the page never jumps |
| `focus` | the point a crop keeps in view (§3.3); the centre until someone taps elsewhere |
| `alt` | the writer; **prefilled** from the file name, flagged in the library while it is still that |
| `credit` | the writer; asked for once at upload ("Who took it?"), remembered for the next upload |
| `taken_on` | the camera's date, kept before EXIF is dropped (the location never is) — sorts a regatta's photos |
| `phash` | a perceptual hash: the same photo uploaded twice is **the same entry**, offered instead of a copy |
| `uploaded_by`, `created_at` | the request |

The site's own pictures (`web/src/content`, `DSBL_PHOTOS`, `OWN_PHOTOS`) are seeded as
entries with `source = site`: shown like the rest, not deletable.

### 2.2 One picker, everywhere

The toolbar's picture button, the post's cover and a pasted web picture all open **one
panel** beside the text (not a modal — the site has none):

- recent first, a search box over name, alt and credit, the regatta's date;
- drop or paste right into the panel to upload; several at once;
- **drag a tile into the text**, or click it to insert at the cursor;
- the tile says where else it is used ("in 2 posts").

The editor's existing paths stay: a picture dropped or pasted straight onto the text is
uploaded **into the library** and inserted, without the panel ever opening.

### 2.3 Sources: one import API, many feeders

Pictures from outside — a photographer at the regatta, a Nextcloud folder, a Flickr album,
Wikimedia Commons — arrive through **one endpoint for machines**, `POST
/api/import/media`, authorised by an **import key** editorial makes and revokes (decided
2026-10-19). The site itself knows no Nextcloud and no Flickr: each source is a small
feeder that calls this API, so a new source is a new feeder, never a change to the
library.

- The key travels in `X-Import-Key`, never as a person's sign-in; only its hash is stored,
  and it is shown once.
- A feeder may send its own id for a picture: the same id twice answers the entry already
  made, so a feeder that retries or re-scans a folder never duplicates.
- **The first feeder is ours**: an upload page (`/upload#key=…`) a photographer opens from
  a link on the phone, drops pictures, names the credit once, done. It uses the import API
  and nothing else, which keeps the API honest.
- Later feeders, each only when asked for: a Nextcloud folder watched by a job (WebDAV,
  `nc_py_api`), a Flickr album, Wikimedia Commons (licence and author → credit). Each
  copies; none hot-links (reliability, EXIF, the sizes of §1.5).

### 2.3 The *Media* tab

In the administration, for editorial: the grid, a filter "no alt text yet" / "not used",
an entry's page to correct alt, credit and focus, and the posts it appears in. **Delete is
refused while a post uses it**, listing those posts. *Used in* is computed from the posts
on every look, never stored — a deleted post frees its pictures on its own.

## 3. Automatic layout

### 3.1 One picture

Decided by its shape (`width / height`) and its pixels against the text column
(~42 rem on a desktop, the full width on a phone):

| The picture | Shown | Why |
|---|---|---|
| **landscape** (ratio ≥ 1.2) | the column's full width | the normal case — a boat, a start |
| **panorama** (ratio ≥ 2) | wider than the text on a desktop, edge to edge on a phone | a wide shot earns the room |
| **portrait or square** | centred, at most 70 % of the screen's height | a phone's upright photo would otherwise fill three screens |
| **small** (narrower than the column) | its own size, centred, never blown up | a logo, a chart, a screenshot stays sharp |

The rule is one CSS class the server adds on read (`shape-wide`, `shape-pano`,
`shape-tall`, `shape-small`) and a `--ratio`; the editor's picture node gets the same from
the upload's answer, so **what editorial sees while writing is what the reader gets**.

### 3.2 Several pictures: a gallery that justifies itself

A gallery lays its pictures out in **rows of equal height that fill the width exactly**,
each picture as wide as its shape asks — the arrangement photo sites use, done in plain
CSS: each item gets `flex-grow` and `flex-basis` proportional to its ratio, so no
picture is cropped and no row has a gap. Two to three per row on a desktop, two on a
phone; one alone on the last row is not stretched.

- **Tap → full screen**, swipe through every picture of the post (a lightbox, with the
  credit), on the public page only.
- **The caption is automatic**: the credit — one line for the whole gallery ("Photos:
  A. Example, B. Sample") rather than a credit under each.
- In the editor a gallery is one block: drag pictures inside it to reorder, out of it to
  stand alone.

### 3.3 Crops keep what matters

Where a frame has a fixed shape — the post's cover on a card (3:2), the article's header,
the league's page — the picture is cropped with `object-position` at its **focus**. The
focus starts in the centre; one tap on the picture in the library moves it (the bow, the
helm's face). Phase 3 can guess it on upload (a saliency crop, `smartcrop`-style, MIT) so
the tap is rarely needed.

### 3.4 Loading

On read every picture gets `width`/`height` (no jump), `srcset` over its variants with
`sizes` from its shape (a gallery tile asks for 480 px, a panorama for 2400), `loading=
"lazy"` below the first screen, and its placeholder colour behind it.

## 4. Data model (sketch, `app/models/editorial.py`)

```
MediaItem
  id, name (random), source: upload | site, owner: site (later club:<id>)
  original_name, alt, credit, taken_on
  width, height, focus_x, focus_y (0..1), placeholder, phash
  uploaded_by_user_id, created_at
```

Variants are files under `uploads/media/<name>-<width>.webp`, derived from the stored
master (2400 px JPEG); a lost variant is rebuilt on request, so the directory is a cache
of the master. `Post.photo_url` becomes `Post.photo_id` (a `MediaItem`), and the text's
`<img>` points at `/api/media/<id>`. Uploads made before this have no entry; nothing is in
production, so the seed is regenerated rather than migrated.

Endpoints: `GET|POST /api/admin/media` (list with search; upload, answering the existing
entry for a duplicate), `GET|PATCH|DELETE /api/admin/media/{id}`, and the public
`GET /api/media/{id}/{width}.webp`.

## 5. Phases

1. **The library and the import API** (Story R-2) — `MediaItem`, upload into it from every
   existing path, import keys and `POST /api/import/media`, our upload page as the first
   feeder, the *Media* tab, alt and credit, *used in*, the delete guard, duplicates. Then
   the picker panel, and the editor storing references.
2. **Automatic layout** — shapes and the read-time expansion (§3.1, §3.4), the gallery
   node and its justified rows (§3.2), the lightbox.
3. **Crops** — focus by tap, then guessed on upload (§3.3).
4. **Only if asked for** — alt text *suggested* on upload by a vision model (Claude), for
   editorial to confirm, never published unconfirmed; a web picture pasted into the text
   fetched into the library instead of hot-linked (needs SSRF guarding: public addresses
   only, size and time limits).

## 6. What is deliberately not here

- **Sizes, alignment, text flowing beside a picture.** §3 decides; a choice would be
  made differently by every writer and break on every phone.
- **Folders and tags.** Search over name, alt, credit and date is enough for the few
  hundred pictures a season produces.
- **Editing pixels** — crop, rotate, filters. The focus point is the one crop the site
  needs; the rest is done before the upload.
- **Video.** Videos are YouTube embeds (`web/src/content`), and stay so.

## 7. Open questions

- **Is a credit required?** A press photo without one is a legal risk; a member's phone
  snap is not. Proposal: asked at upload, not enforced, flagged in the library.
- **Who may use the library besides editorial** — the clubs, once they have pages?
- **Retention** of unused uploads: kept until deleted, or listed for deletion after a
  season?
